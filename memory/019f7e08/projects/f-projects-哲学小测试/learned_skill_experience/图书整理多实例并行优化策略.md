## 输入
- 需要提升图书整理流程的整体吞吐率
- 存在快通道（纯 IO）与精修链（AI 计算）两种不同负载类型

## 步骤
1. **评估瓶颈**：确认当前流程瓶颈是 IO 等待（磁盘/网络）还是 CPU/AI 等待。
2. **选择并线模式**：
   - 若需加速单一环节（如快通道积压）：启动多个 `--instance N` 实例并行处理同一类任务（利用文件认领锁自动分流）。
   - 若需提升整体效率：同时运行快通道实例与精修链实例（两者负载互补，互不阻塞），一个实例搬新书、另一个实例 AI 修旧书。
3. **错峰启动**：精修实例启动时若投放区还有散文件待快通道搬，先等 60 秒再开工错峰（`_quick_buffer_wait` + `_QUICK_BUFFER_SEC`）；无待搬文件直接启动。
4. **监控竞态**：同名文件落点用原子占位（O_CREAT|O_EXCL 创建占位 → os.replace 覆盖），防多实例同搬同名覆盖；内容收集器可加 first_only 早退供存在性探测。

## 输出
- 系统吞吐量显著提升（接近线性加速比，受限于磁盘/网络带宽）
- 避免单实例排队导致的资源闲置

## 注意事项
- **架构基础**：项目已内置 `instance_lock` 机制（文件认领 + 发布锁），无需修改代码即可安全多开。
- **隔离原理**：快通道只碰库外投放区、精修只碰库内未分类区（空间分离）；先落地后登记、精修只认库记录（时序隔离）——"搬运中精修读同一文件"在机制上不存在。
- **收益递减**：超过 3 路并行可能因磁盘/网络带宽封顶导致收益下降甚至抖动。
- **推荐组合**：优先采用"快通道实例 + 精修链实例"的组合，而非单纯增加快通道实例数量。
- **数据库锁**：SQLite 写库已配置 30 秒超时；AI 长会话只持文件认领锁、不持库锁，都是毫秒级短事务。
