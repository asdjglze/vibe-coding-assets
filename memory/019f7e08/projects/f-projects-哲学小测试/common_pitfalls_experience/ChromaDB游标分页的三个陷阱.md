## 使用场景
基于ChromaDB存储的消息类数据实现游标分页（滚动加载历史记录）时。

## 三个必踩的坑
1. ChromaDB where 过滤的 $lt/$gt 操作符只支持 int/float 数值，字符串时间戳比较会报错 "Expected operand value to be an int or a float"，时间游标必须在应用层内存过滤（全量拉取后按时间字符串比较）。
2. ChromaDB collection.get 不保证返回顺序（通常按插入序），如果直接传 limit 参数，截断的是最老的记录，导致最新的消息被丢弃；必须不带 limit 全量拉取后在应用层按时间戳排序再截断。
3. 后端 has_more（是否还有更早消息）判断必须在内部消息过滤之前进行：若在过滤 system 等内部消息后判断，过滤导致的条数缩减会让 has_more 永远为 false，前端滚动到底不触发加载。
4. 附带原则：ChromaDB where 多字段条件必须用 $and 语法包数组（where 本身只支持单字段）。

## 说明
单用户消息量在几千条以内时，全量拉取+内存过滤排序的方案性能完全可接受（毫秒级），比引入数值时间戳迁移更简单可靠。前端滚动加载还需配合：滚动到顶阈值触发、加载中/没有更多的视觉反馈、内容不足一屏时自动补加载。
